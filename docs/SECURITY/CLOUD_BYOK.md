# Cloud BYOK

Bring your own key (10.0.0-beta): a KMS key's material is imported into a
cloud KMS by that cloud's own import protocol. The KMS key is the source of
truth; the cloud holds a wrapped-then-unwrapped copy inside its HSM, and the
KMS records which KMS key version is behind each piece of cloud material
(custody).

The design follows the owner's reference, a console that drives AWS KMS
imports from a Securosys Primus HSM through its Transaction Security Broker
(owner directive, 2026-10-11). Here it covers every cloud the KMS connects to,
and has no TSB: material comes from the KMS's own DRBG or from any PKCS#11 HSM
through `hsm-connector`.

## Where the material comes from

| Source | Generated by | Wrapped by | Leaves as |
|---|---|---|---|
| KMS | keycore's DRBG (a key created with `export_allowed`) | keycore, `pkg/crypto.WrapForCloudImport` | ciphertext under the cloud's wrapping key |
| HSM | the customer's PKCS#11 HSM: a key created with `hsm: true` and `export_allowed: true` is generated **sensitive and extractable** (`CKA_SENSITIVE`, `CKA_EXTRACTABLE`) and labelled `hsm_cloud_import: allowed` | the HSM, `C_WrapKey` with the cloud's public key loaded as a session object (`pkg/hsmconnector/byok.go`) | ciphertext under the cloud's wrapping key; the value never exists outside the two HSMs |

Every other HSM key stays non-extractable. Switching an existing HSM key's
export policy on does not make it leave: the HSM refuses (`key_not_extractable`),
because extractability is fixed when the HSM generates the key. Rotations of a
cloud-import HSM key are generated the same way (`rotateHSMKey`). `hsm*` labels
are never taken from a caller.

## The wrap: one keycore decision

`POST /keys/{id}/cloud-wrap` (keycore, route kernel, `key.cloud_import`) is the
only way material leaves for a cloud:

- **Caller**: only the `kms-cloud` service identity (`caller_not_allowed`
  otherwise). The cloud service fetched the wrapping key from the cloud itself.
- **User**: the cloud service forwards the user's verified token with the
  delegated usage `cloud-import` (`pkg/delegation`); the user's grants must
  allow `cloud-import` (base operation `export` for workload tokens). The
  decision is keycore's (KEY_ACCESS_MODEL.md section 5).
- **Checks**: every export check (posture step-up and sync pause, the key
  access decision, the key's export policy, the tenant's policy), then the
  FIPS mode for the scheme.
- **Version**: the current one, or an earlier one to renew or restore the same
  material. A destroyed version is refused.
- **Audit**: `audit.key.cloud_wrapped` with `version`, `scheme`, `source`,
  `kcv`, `material_format` and the SHA-256 fingerprint of the cloud's
  wrapping key; refusals with their reason.

### Schemes

| Scheme (`pkg/crypto`) | Construction | Used by | FIPS strict mode, KMS source |
|---|---|---|---|
| `rsa-oaep-sha256` | RSA-OAEP, SHA-256, MGF1-SHA-256 | AWS (RSAES_OAEP_SHA_256), Alibaba, Google (RSA_OAEP_3072_SHA256), OCI (RSA_OAEP_SHA256) | allowed (module) |
| `rsa-aes-kwp-sha256` | CKM_RSA_AES_KEY_WRAP: a fresh AES-256 key under RSA-OAEP SHA-256, the material under it with AES key wrap with padding (RFC 5649) | private keys: AWS (RSA_AES_KEY_WRAP_SHA_256), Google (RSA_OAEP_3072_SHA256_AES_256) | refused (KWP is built on the module's AES, not a module service) |
| `rsa-aes-kwp-sha1` | the same with SHA-1 in OAEP | Azure Key Vault / Managed HSM (`CKM_RSA_AES_KEY_WRAP`) | refused |
| `rsa-oaep-sha1` | RSA-OAEP, SHA-1 | Salesforce Shield | refused |

In the HSM the same constructions run as `CKM_RSA_PKCS_OAEP`, and
`CKM_AES_KEY_WRAP_PAD` under a session AES key that is then wrapped with
`CKM_RSA_PKCS_OAEP` and destroyed. Strict mode does not refuse the HSM path:
the HSM is the module doing the cryptography. The refusal for the KMS path is
listed in `pkg/fips/impact.go`.

## Each cloud

| Cloud | Key before material | Import | New material | Kill switch | Restore | Expiry | Verify |
|---|---|---|---|---|---|---|---|
| AWS KMS | `CreateKey` origin EXTERNAL | `GetParametersForImport` (RSA-4096) → `ImportKeyMaterial` | `NEW_KEY_MATERIAL` + `RotateKeyOnDemand` | `DeleteImportedKeyMaterial` | reimport the same version | yes (≤ 365 days) | encrypt/decrypt, MAC, sign/verify |
| Google Cloud KMS | import-only CryptoKey, no initial version | import job (Google's HSM generates the RSA-3072 key) → `ImportCryptoKeyVersion` | new version + primary | `DestroyCryptoKeyVersion` | `RestoreCryptoKeyVersion` while scheduled; reimport into the destroyed version after | no | encrypt/decrypt, MAC, asymmetric sign checked under the version's public key |
| Azure Key Vault / Managed HSM | created on import | temporary RSA-HSM KEK (`import` only) → transfer blob in `key_hsm` → KEK deleted | a new key version | the version is **disabled** (Azure can't remove material) | re-enabled | yes | wrapkey/unwrapkey, sign/verify |
| OCI Vault | created on import | the vault's wrapping key → `ImportKey` | `ImportKeyVersion` | the key is **disabled** | enabled | no | encrypt/decrypt on the crypto endpoint |
| Alibaba Cloud KMS | `CreateKey` origin EXTERNAL | `GetParametersForImport` (RSA-2048) → `ImportKeyMaterial` | not supported by Alibaba: refused | `DeleteKeyMaterial` | reimport | yes | encrypt/decrypt |
| Salesforce Shield | the BYOK certificate from Setup (public, given with the request) | `TenantSecret` with `SecretValue`, `SecretValueCertificate`, `SecretValueHash` (SHA-256 of the secret, computed in keycore or with `C_DigestKey` in the HSM) | a new tenant secret | not offered (Setup only) | not offered | no | not offered (no API) |

An operation a cloud doesn't support is refused (`operation_not_supported`)
and not offered in the dashboard. Key specs per cloud are listed by
`GET /cloud/byok/providers`; AES-256 goes everywhere.

Credentials come only from Playbooks → Credentials. Optional fields the BYOK
engine reads: AWS `endpoint_url`, Alibaba `endpoint_url` (VPC endpoint),
Google `endpoint` (private endpoint), OCI `crypto_endpoint` (needed to verify).

## Runs and custody

Every operation (`create`, `rotate`, `reimport`, `revoke`, `restore`,
`verify`, `sync`) is a run of named steps, each recorded with the call it made
and its command-line equivalent; the dashboard exports them as a script.
Tables (`migrations/004_byok.sql`, replicated under `byok`):
`cloud_byok_keys`, `cloud_byok_materials` (custody: KMS version, KCV, cloud
material ID, state, scheme, source, wrapping key fingerprint),
`cloud_byok_runs`.

A failure part-way leaves what was done: a cloud key created before a refused
wrap stays "waiting for material"; once the cause is fixed, `reimport` imports
into it. The temporary Azure KEK is deleted whatever the import did.

Cloud keys created by releases before 10.0.0-beta were generated by the cloud
(the old "import" called `CreateKey` natively). They are listed read-only as
`cloud-generated`; BYOK operations refuse them.

## Audit

`audit.cloud.byok_created`, `byok_rotated`, `byok_reimported`,
`byok_revoked` (critical), `byok_restored`, `byok_verified`, `byok_synced`,
`byok_keys_listed`, `byok_key_read`, `byok_runs_listed`,
`byok_providers_read`: route kernel events with `run_id`, `key_id`,
`cloud_key_id`, `provider`, `material_id`; refusals carry `reason`; a failed
run is `result: failure` with the failing step. `audit.key.cloud_wrapped`
(keycore) and `audit.hsm.key_wrapped_for_cloud` (hsm-connector) record the
wrap. Playbook triggers: `byok_material_imported`, `byok_material_revoked`.

## Evidence

- `pkg/crypto`: RFC 5649 vectors, round trips per scheme, strict-mode refusals
  (`TestKWPRFC5649Vectors`, `TestWrapForCloudImportRoundTrips`,
  `TestCloudWrapRefusedInStrictMode`).
- `pkg/hsmconnector` on SoftHSM2 2.7: every scheme wrapped inside the HSM and
  unwrapped to the HSM key's KCV, C_DigestKey, refusals
  (`TestBYOKWrapInsideHSM`, `TestBYOKWrapRefusals`).
- keycore: KMS and HSM paths, versions, caller and policy refusals, strict mode
  (`TestCloudWrapKMSKey`, `TestCloudWrapHSMKey`,
  `TestCloudWrapStrictModeRefusesNonModuleSchemes`).
- services/cloud: each cloud's wire protocol against a double that unwraps
  with its own private key, so the test proves the cloud would receive the KMS
  version's material (`TestBYOKLifecycleAWS` with the unmodified AWS SDK,
  `TestBYOKGoogleCloudImportJobs` over gRPC, `TestBYOKAzureTransferBlob`,
  `TestBYOKOCIVault` with OCI request signing, `TestBYOKAlibaba`,
  `TestBYOKSalesforceTenantSecret`); routes and audit
  (`TestBYOKRoutesAuditEachOperation`, `TestBYOKRoutesRefusalsAudited`);
  Postgres storage (`TestBYOKStorePostgres`).

## Open

- **Not yet run against real cloud accounts.** The protocol doubles prove the
  wire format and the cryptography; a manual workflow against real accounts
  (as for storage credentials in 9.3.0-beta) is next.
- The Azure scheme is `CKM_RSA_AES_KEY_WRAP` with SHA-1 OAEP as Key Vault's
  BYOK specification describes; Managed HSM's SHA-256 variant is not offered.
- Still to build (owner's scope, 2026-10-11): cloud key pages (policy, grants,
  aliases, tags, enable/disable, deletion, a "try it" panel), a structured
  per-cloud console of typed, allow-listed operations, and automation (renew
  before expiry, rotate on an interval) as playbook actions.
- Asymmetric BYOK of KMS private keys needs PKCS#8 material and a KWP scheme,
  so it is refused in strict mode unless the key is in an HSM.
